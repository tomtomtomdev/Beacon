## Decisions log

- **2026-09-02 (sponsorship detector — residency preconditions)** — **"Already be based in X" is now `explicit_no`.** Found while tailoring a CV against the live shortlist: Bjak's "AI Neobank App" postings require the candidate to *already live* in the hiring country ("we are hiring specifically for this market, so applicants should already be based in Germany"). Seven of them sat in §4 target countries at **fit 72** tagged `unknown` — sorting as neutral while being flatly unreachable, which is the worst failure mode for a tool whose entire purpose is leaving one country for another. The phrasing names no sponsorship word, so neither the negator×object table nor the work-authorization table could see it.
  **The first attempt was wrong and the spot check is what caught it.** Generating modal × verb (`must|should|required to` × `be based|be located|reside`) flipped **23 of 8,918** live postings wrongly: Discord ×21 says "Candidates must reside in **or be willing to relocate to** the San Francisco Bay Area" (an explicit relocation *offer*), and Anthropic's "Must be located in San Francisco" appears on postings that also read "We do sponsor visas!". Because `explicit_no` beats `explicit_yes` by pinned precedence, shipping that would have silently inverted a whole class of reachable sponsoring jobs into refusals — invisible, because the tier looks deliberate. **The discriminator is the word "already"**, which separates "you must already live here" from a plain statement of where the desk is. Narrowed accordingly: **19 flips, all Bjak, zero false positives**; the three rejected phrasings are now negative-control rows in `test_a_location_requirement_without_already_is_not_a_refusal`. Live `scripts/spot_check_sponsorship.py` clean (30 sampled, 26 yes / 4 no, Anthropic still `explicit_yes`). Precedence, `sort_rank` and the tier resolver are untouched — this adds phrase-table rows only, per CLAUDE.md's "data, not a branch". Backend **712 → 722**.

- **2026-08-31 (run.sh)** — **`run.sh` now serves the cached `beacon.db` immediately and refreshes from the source APIs in the background**, instead of blocking the whole launch on a full poll. `beacon.db` was always the cache; the only reason the launch waited was that the poll ran to completion before uvicorn started. Two things made the concurrent version safe. (1) **SQLite is now opened in WAL mode** (`journal_mode = WAL` + `busy_timeout = 5000` in `connect()`): the live DB was in `delete` mode, where a writer's lock shuts readers out, so serving the UI during a poll would have produced `database is locked` on `/jobs` rather than cached rows. WAL gives a reader the last committed snapshot for the length of the poll; `busy_timeout` covers the writer-vs-writer case (an API write — a saved search, a settings change — landing mid-poll waits its turn instead of raising). Guarded by two tests in `tests/integration/test_db_connect.py`, the first a RED that reproduced the lockout. WAL is persistent in the file, so it also applies to the scheduler and every CLI entrypoint; `backup.py` is unaffected because it already uses sqlite's **online backup API**, which is WAL-consistent (a plain file copy would not have been — hence the `-wal`/`-shm` entries added to `.gitignore`). (2) **First run still blocks**: with no `beacon.db` there is nothing cached to serve, so a background refresh would just serve an empty UI. `--wait-ingest` restores the old blocking behaviour on demand; `--no-ingest` is unchanged. Refresh output goes to `.ingest.log` (redirected so it cannot interleave with the Vite dev-server log) with a one-line green/amber verdict printed when the poll lands. **Not changed: the frontend does not live-update.** Fresh rows appear on reload, or when the tab regains focus (TanStack Query's default `refetchOnWindowFocus`) — the run.sh verdict line says so. Polling or an SSE nudge is a UI decision, deliberately left out of a launcher fix.

- **2026-08-26 (fix)** — **`/jobs` 500s under `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread.`** Not a repo bug: `get_db` already opens one connection per request and closes it in the `finally`. The cause is the ASGI hop count — FastAPI resolves a **sync** `Depends` and runs a **sync** endpoint as two separate `run_in_threadpool` calls, and anyio is free to place them on different worker threads, so the connection is opened in thread A and queried in thread B. It only surfaces under concurrency (the frontend firing several `/jobs` requests at once), which is why the suite and single-request use never caught it. Fix is one flag, `check_same_thread=False` in `connect()`, with the reasoning written into the docstring: sqlite's guard assumes a shared connection, but nothing here shares one — the API opens one per request and the event loop serialises that request's dependency, endpoint and teardown; the CLI entrypoints and scripts open their own; there is no other threading in `beacon/`. Guarded by `tests/integration/test_db_connect.py`, which reproduces the exact production traceback as a RED before the flag. `backup.py` deliberately keeps its own bare `sqlite3.connect` (it wants no row factory and no foreign-key pragma) and was left alone.

- **2026-08-18 (sponsorship-negation)** — **The explicit-NO table is now GENERATED from negator × object with a bounded gap; a refusal phrased without the word "sponsor" no longer inverts to `explicit_yes`.** Found while checking freshness on the `explicit_yes` iOS roles: Airbnb's "Senior iOS Engineer, Global Markets" carried tier `explicit_yes` with evidence reading **`NOTE: NO VISA SUPPORT`**.
